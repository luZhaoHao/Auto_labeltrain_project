# Auto-Tune 生态产品路线图（2026-08-20 修订）

> 本文档维护 Auto-Tune 生态的产品边界、阶段路线与兼容原则。当前稳定版本与开发注意事项见 `docs/development_handoff_20260814.md`；具体批次任务与验收顺序见 `docs/implementation_plan_20260814.md`。

## 1. 核心结论

Auto-Tune 后续不再按照“单一主程序 + C2/C3 扩展包”发展，而是形成同一生态下三款可以分别安装、运行、测试和发布的软件：

1. **Auto-Tune Studio**：面向操作人员和算法工程师的离线单机训练产品。
2. **Auto-Tune Research**：面向科研人员的模型结构实验与自动研究产品。
3. **Auto-Tune Cloud**：面向团队和组织的多用户训练、标注协同与算力调度平台。

三款软件共享品牌、概念模型和版本化数据协议，但不互相构成安装依赖。任意一款软件均可单独交付；安装 Research 或 Cloud 不是使用 Studio 的前提，Cloud 也不要求用户先部署 Studio。

## 2. 当前基线

### 2.1 Studio v0.1 已完成

- Module A：数据集质量、bbox、类别分布和特征聚类分析。
- Module B：指标摘要、文本诊断和视觉大模型分析。
- Module C：感知、LLM 决策、Guardrails、训练执行和探针监控。
- A0 审计闭环：候选参数、护栏值、实际参数、精确命令、before/after/delta、失败终态和敏感字段脱敏。
- 普通训练与自动调优统一收尾：统一 KPI、experiment history、Module B 分析、结构化错误与历史页面。
- 当前架构：FastAPI + Jinja2、JSON 文件、本地 subprocess、SSE；单用户、单机、无数据库和任务队列。

上述能力是 Studio 的稳定兼容边界。后续不得因为 Research 或 Cloud 的建设而破坏其离线单机可用性。

### 2.2 Studio 离线定义

Studio 的核心数据分析、训练、历史与报告能力在本机完成。仅外部大模型调用、未随安装包提供的资源获取以及用户主动更新可能联网。正式发行包应提供依赖与模型资源准备说明，不得将云端服务作为本地训练闭环的隐含前提。

## 3. 三款软件的产品边界

| 维度 | Auto-Tune Studio | Auto-Tune Research | Auto-Tune Cloud |
|---|---|---|---|
| 核心用户 | 操作人员、算法工程师 | 研究人员、论文与算法团队 | 企业团队、平台管理员、标注与训练团队 |
| 主要价值 | 安全完成数据分析、训练和超参数优化 | 自动提出、执行和比较结构实验 | 集中管理用户、数据、标注、任务和GPU资源 |
| 安装形态 | Windows/Linux 单机安装包 | 独立研究环境或容器 | 独立服务器/私有云部署 |
| 联网要求 | 除外部LLM外可离线 | 可本地运行，外部服务按需联网 | 通过局域网或网络提供平台服务 |
| 数据层 | 本地目录与轻量历史 | 实验账本、结构版本、产物索引 | PostgreSQL、对象存储、队列 |
| LLM动作空间 | 白名单内超参数 | 结构配置、注册模块，后期受控代码修改 | 调度与协同建议，不绕过权限执行 |
| 失败策略 | 关键失败阻止训练 | keep/discard/crash/invalid/review | 重试、隔离、恢复、告警和审计 |
| 发布节奏 | 稳定版本优先 | 研究能力独立迭代 | 平台里程碑独立发布 |

### 3.1 Auto-Tune Studio

Studio 保持“确定性执行器 + 受约束 LLM 决策”的设计。大模型只能提交结构化候选参数，必须经过 Schema、白名单、Guardrails、审计持久化和训练预检后执行。

近期范围：

- ✅ 训练日志精简与完整日志折叠（Studio S1.1，2026-08-20 已验收）；
- ✅ 不可变数据快照（Studio S1.2，2026-08-21 已验收，待与 S1.3 一并提交），停止移动原始数据；
- ✅ API 凭据安全（Studio S1.3，2026-08-21 已验收，待与 S1.2 联合提交）：Windows Credential Manager、环境变量覆盖、客户设置入口、Endpoint 策略、明文迁移与轮换；
- 目录选择及容量、成员数量限制；
- YOLO11/YOLO26 与 task/version 配置框架；
- 根据真实需求扩展分割、OBB和分类；
- 明确调优目标、试验预算、重复配置检测和最终调优总结。

明确不纳入 Studio 核心：任意代码改写、多用户认证、GPU集群调度、CVAT服务端融合和自动论文实验。

#### 3.1.2 YOLO版本与任务兼容矩阵

版本和任务必须分为“框架支持”和“真实验收”两层，不能只在下拉框出现模型名称就宣称支持。

| 版本/任务 | Detect | Segment | OBB | Classify | 主要改动 |
|---|---|---|---|---|---|
| YOLOv8 | 已有基线 | 待实现 | 待实现 | 待实现 | 保持现有detect不回归，补各任务模型和解析 |
| YOLO11 | 待实现 | 待实现 | 待实现 | 待实现 | 模型目录、task/version、UI、短epoch验证 |
| YOLO26 | 待实现 | 待实现 | 待实现 | 待实现 | 先确认Ultralytics版本和模型可用性，再适配 |
| YOLOv5 | 遗留兼容，后置 | 另行评估 | 不优先 | 另行评估 | 独立`train.py`命令和不同results.csv字段 |

任务改造范围：

- **Detect**：作为所有版本的回归基线，保持四项KPI、审计和统一历史一致。
- **Segment**：Module A解析多边形标签，数据预览支持mask，Module B/C适配分割指标与损失列。
- **OBB**：解析旋转框标签和角度，补旋转框可视化、指标映射和任务模型。
- **Classify**：重新处理按类别目录组织的数据、top1/top5指标、评分、报告和UI，不能沿用检测任务假设。
- **YOLOv5**：通过独立适配器构造命令并映射旧版指标，不把兼容分支散落到通用执行器。

每个“已支持”单元必须至少完成：最小合法数据集、短epoch训练、结果解析、Module B报告、统一历史、失败路径和UI选择测试。

#### 3.1.3 Studio本地SQLite与多数据集

SQLite仍有价值，但用途从原计划的“本地与在线共用数据库”调整为 **Studio本地实验索引库**：

- 管理多个数据集的名称、路径引用、快照身份、任务类型、校验状态和最近使用时间；
- 索引训练运行、调优会话、报告、权重和产物位置；
- 支持历史筛选、运行对比、标签和归档状态；
- 保留JSON审计记录作为可移植事实文件，SQLite不取代A0审计；
- 提供JSON历史到SQLite的幂等迁移和损坏文件只读保护；
- 数据库只服务本机单用户，不加入用户、角色、JWT或租户权限。

Cloud不复用Studio的SQLite实现。Cloud的数据模型将在C0评审后以PostgreSQL等服务端数据库落地，通过生态协议与Studio交换数据。

#### 3.1.4 Linux与跨平台适配

Linux适配仍属于Studio正式交付范围，同时为Research本地环境和Cloud Worker提供基础：

1. 新增`environment-linux.yml`，移除Windows专属依赖并明确CPU/GPU PyTorch安装方式；
2. 提供`setup.sh`、`start_server.sh`、`start_app.sh`、`run_tests.sh`和`build_package.sh`；
3. 文件夹浏览器支持`/`、用户目录、Linux权限和根目录父级语义；
4. 清理测试与辅助脚本中的Windows绝对路径、盘符、反斜杠和GBK假设；
5. 处理文件名大小写、`.jpg`/`.JPG`、符号链接和路径权限差异；
6. 支持`0.0.0.0`局域网监听，但默认部署仍需提示访问控制风险；
7. 在目标Linux发行版上完成环境创建、启动、目录选择、pytest和短epoch训练。
8. 增加 S1.3.1 跨平台凭据适配：Linux桌面优先 Secret Service/libsecret；Docker和无桌面Linux支持 `AUTO_TUNE_TEXT_API_KEY_FILE` / `AUTO_TUNE_VISION_API_KEY_FILE` 只读 Secret挂载，禁止把 Key写入镜像层或项目 `.env`。

原“0.5–1天”只覆盖脚本和少量代码修改。若包含真实GPU环境、安装包、兼容测试和用户文档，应按3–7人日估算。

#### 3.1.5 安装、升级与卸载

Studio必须从“源码可运行”走向“操作人员可安装”：

| 交付项 | Windows | Linux | 验收要求 |
|---|---|---|---|
| 联网安装 | `setup.bat`或安装器 | `setup.sh` | 依赖失败可诊断，可重复执行 |
| 离线安装 | 运行环境、依赖、可选权重打包 | 离线包/内部镜像 | 断网环境完成核心训练闭环 |
| 首次向导 | 目录、设备、LLM配置、模型资源检测 | 同等能力 | 不要求用户直接编辑真实`config.yaml`密钥 |
| 环境检测 | Python、CUDA、GPU、磁盘、端口 | Python、驱动、CUDA、权限、端口 | 给出可操作修复建议 |
| 启动/停止 | 快捷脚本和明确终止方式 | 服务脚本；可选systemd | 不遗留孤儿训练进程 |
| 升级 | 配置、Schema和历史迁移 | 同等能力 | 失败可回退，旧记录可读 |
| 卸载 | 程序与用户数据分离 | 同等能力 | 默认不删除数据集、权重和历史 |

配套文档至少包括：快速开始、操作手册、管理员安装指南、离线部署指南、Linux指南、配置参考、故障排查、升级迁移和数据备份恢复。

#### 3.1.6 数据、训练与体验增强

- 正式数据接入继续采用目录选择；拖拽仅用于路径选择或受限文件导入，ZIP只保留遗留兼容。
- 多数据集列表、数据校验状态、快照和最近运行应在Studio本地可管理。
- 增加一键分析编排，但必须显示每一步状态，允许跳过外部LLM步骤。
- 训练中断、页面刷新和SSE重连后应从持久化状态恢复显示；不能仅依赖浏览器内存。
- 支持训练对比、报告导出、权重与配置导出，并记录产物校验摘要。
- Module A/B/C的LLM提示词、诊断规则和视觉分析能力可持续迭代，但不得覆盖确定性事实层。

### 3.2 Auto-Tune Research

Research 独立承接原“模型结构实验平台”方向，并参考 AgentHPO 与 autoresearch 的实验循环：提出方案、执行实验、读取证据、保留或放弃、形成可复现结论。

1. **R0 研究协议**：固定数据划分、评估函数、主指标、资源预算与实验账本。
2. **R1 结构解析**：解析 YOLO 模型结构、模块拓扑、参数量和计算量。
3. **R2 受控结构组合**：通过注册模块和模板生成 Backbone、Neck、Attention、算子与 Loss 变体。
4. **R3 自动消融**：baseline 与变体批量比较，记录 keep/discard/crash/invalid/review。
5. **R4 受控代码研究**：仅在隔离工作区和资源沙箱内开放有限代码修改，禁止改写评估事实层。

Research 必须同时记录检测指标、参数量、FLOPs、显存、训练时长、推理速度和结构复杂度，不能只以单一精度指标决定保留实验。

### 3.3 Auto-Tune Cloud

Cloud 是独立的平台工程，不再描述为 Studio 的“在线模式”。它可以复用经抽离和版本化的算法能力，但用户体系、数据库、队列、对象存储、训练 Worker 和权限审计必须按服务端架构独立建设。

1. **C0 架构验证**：API契约、任务状态机、租户边界、Worker协议和部署拓扑。
2. **C1 平台基础**：认证授权、项目/数据集、对象存储、训练队列、GPU调度、重启恢复和审计。
3. **C2 CVAT解耦集成**：CVAT导出到训练、模型回传自动标注、服务鉴权和异步状态同步。
4. **C3 运营能力**：配额、成本、告警、监控、备份恢复和多节点扩展。

CVAT 保持独立系统，通过 API 和异步任务解耦集成；不合并其 Django/PostgreSQL/Redis/React 代码库。

## 4. 共享生态协议

三款软件共享的是版本化协议，而不是统一安装程序。协议至少包含：

- `DatasetSnapshot`：数据集身份、划分、校验摘要和来源；
- `ExperimentSpec`：目标、参数或结构变更、预算和约束；
- `TrainingManifest`：运行环境、命令、配置和事实来源；
- `TrialRecord`：状态、指标、资源消耗、结论和父实验；
- `TrainingEvent`：阶段、严重级别、事件类型、指标、证据与建议；
- `AgentDecision`：诊断、候选动作、理由、护栏结果和最终动作；
- `ArtifactManifest`：权重、报告、曲线、日志和结构文件；
- `AuditRecord`：执行事实与结构化错误。

协议要求：Schema有独立版本号，新增字段保持旧记录可读；缺失值与真实零值区分；时间带时区；指标注明最终轮、最佳轮或聚合口径；本地路径不作为跨软件永久标识；Trackio、MLflow等仅作为可选适配器。

## 5. 推荐开发顺序

```text
共同前置：冻结 v1 生态协议最小集合
        │
        ├─ Studio S1：完成剩余可靠性事项
        │      └─ Studio S2：YOLO版本与任务框架
        │
        ├─ Research R0/R1：研究协议与结构解析
        │      └─ R2/R3：受控组合与自动消融
        │
        └─ Cloud C0：服务端架构验证
               └─ C1：平台基础 → C2：CVAT集成
```

Studio S1 应优先完成。Research 和 Cloud 在协议冻结后可以独立立项，不要求等待彼此完成。资源有限时，建议顺序为 Studio → Research 原型 → Cloud 架构验证；正式 Cloud 开发需单独配置后端、运维和安全投入。

## 7. 风险与边界

### 7.1 Studio

- Ultralytics版本升级可能改变CLI、模型注册和结果列，必须通过兼容适配层隔离。
- LLM建议不能成为训练事实来源；执行参数以护栏后的实际值为准。
- 审计失败仍为fatal，不能为了可用性绕过。

### 7.2 Research

- 结构变化可能导致预训练权重失配和指标比较失真。
- 自动代码修改存在供应链、任意命令和资源耗尽风险。
- 固定时间预算只保证同一硬件上的相对可比，跨设备必须记录环境。

### 7.3 Cloud

- 多租户目录隔离不足可能造成严重数据泄露。
- subprocess与本地JSON不能直接扩展为可靠队列和平台数据库。
- GPU抢占、孤儿进程、服务重启、幂等重试和对象存储一致性必须进入首期架构。
- CVAT集成需要明确数据所有权、任务状态映射和失败补偿，不能只实现文件导入导出。

## 8. 发布与仓库策略

- 三款软件分别维护版本号、安装说明、变更日志和测试矩阵。
- 早期可置于同一GitHub组织下的独立仓库；是否拆分共享库由实际复用稳定度决定。
- Studio 当前仓库继续只承载已验收的单机产品演进。
- 数据集、标注、权重、训练产物、日志、审计运行文件和真实凭据不得进入公开仓库。
- 生态协议变更需记录兼容性影响，并为旧记录提供读取或迁移策略。
