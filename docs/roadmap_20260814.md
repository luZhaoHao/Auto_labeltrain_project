## F1.2 Windows Docker 与 ONNX 模型导出交付

F1.2 在 F1.1 稳定基线上完成 Windows 安装、启动、配置、升级与卸载，以及单 Docker 镜像在正常启动即申请 GPU 条件下的 Studio、训练、健康检查和持久化目录验证。按艾卡 2026-09-21 最新要求，不交付 CPU 训练或无 GPU Docker 运行模式；GPU 不可用时明确报错，不静默回退。安装或容器化不得改变三条训练路线的其他业务语义，也不得把数据集、模型、密钥、日志或训练产物固化进安装包和镜像。

F1.2 保持单个 Studio 产品形态，Windows 与 Docker 用户都只通过界面操作，不提供、不宣传也不要求调用外部 API。F1.2 不新增面向公司平台的统一 `/api/v1/jobs` 调度层，也不交付仅 API 的 Engine 模式；现有页面内部 HTTP 请求只是实现细节，不作为外部契约。容器只保留运行所需的健康检查。统一任务 Schema、权限、幂等、队列、日志与产物调度转入 Cloud，并与 CVAT 项目、数据集、标注任务、训练触发、状态回写和模型产物回传共同设计，避免先建设脱离 CVAT 业务流的外部 API。

F1.2-A 首先新增独立 PT 转 ONNX 手动导出通道，复用受控权重库上传区；用户上传可信 `.pt`，自行点击导出，同目录得到 `.onnx`。默认 FP32；FP16 仅在实测可用时放入高级选项。不接入训练结果或历史记录，不自动转换全部训练结果；导出失败不得改变训练终态。后续按 Docker 可行性、正式 Docker、Windows 和联合验收顺序推进，详细边界见 [F1.2 规格](f1_2_windows_docker_onnx_spec_20260918.md)。

Windows 直接安装和 Docker 单镜像是两种独立交付。Windows 版不要求 Docker、WSL 或开发机 Conda；Docker 版在 F1.2-C 必须以同一镜像完成真实 GPU 短训练，并以最简合法流程分别覆盖 HPO 和 LLM 调优。Claude Code 负责各批实现与自测，Codex 负责独立验收、项目文档和 Docker 宿主机环境；未经当前批次验收不进入下一批。

## 1. 路线结论

当前开发主线仅支持 **YOLOv8 Detect**。YOLOv5 Detect 不再开发。项目目标依次为：先交付不需要外部 API 调用的单个 Studio 产品，再在 Cloud 阶段结合 CVAT 建设统一调度 API，最终形成可复现且有验证证据的工程项目。轻量 Research 保留，Cloud 作为 CVAT 联动、多人、多 GPU、LLM 服务治理与权限并发的学习实践方向，在 Studio 交付后分批建设。

最终为用户提供三种彼此独立的训练策略：

1. **直接训练**：使用默认参数或用户明确填写的参数。
2. **HPO 调优**：使用确定性搜索流程产生并验证候选参数。
3. **LLM 调优**：基于代码生成的事实包提出受约束的参数建议。

三种策略共享数据快照、训练执行、状态、日志、历史和报告基础设施，但不串联决策。尤其不设计“HPO 结果再交给 LLM 判断”的流程；最终优胜结果按统一指标与确定性规则产生。

## 2. 当前产品边界

- 单用户、单机、离线优先，FastAPI + Jinja2，本地子进程执行训练。

## 5. 关键技术决策

### 5.1 LLM 只负责受约束建议

- 事实由代码采集和计算，LLM 不生成事实。
- 输入事实带来源标识、缺失状态、数据类型和适用任务。
- 输出必须通过版本化 Schema；未知字段、非法类型、越界值和不适用参数直接拒绝。
- 业务校验器复核指标方向、参数依赖、当前值与建议值、运行状态和证据引用。
- 允许一次携带错误原因的纠错重试；仍失败则结束本轮，不启动训练。
- 最终排名、是否改善和停止条件由确定性代码计算，不由 LLM 自评。

### 5.2 HPO 采用 Optuna TPE

Optuna TPE 作为产品级 HPO 引擎，随机搜索作为基线；Ultralytics 内置遗传调优仅用于内部对照，不作为用户业务流程。原因是 Optuna 更适合管理 Detect 的试验、条件参数、持久化、恢复、预算和结果查询，也能继续复用现有训练执行与审计设施。

首版保持简单：小而明确的搜索空间、固定 trial 数、单目标指标、顺序执行；暂不引入 Ray、分布式搜索、多目标优化和激进剪枝。

### 5.3 复用训练核心与版本化协议

Studio、Research 与 Cloud 复用运行身份、训练执行、指标、数据快照和产物协议。研究实验与云端调度各自维护编排逻辑；不为未规划任务提前建设适配框架。Cloud 的任务权限、资源占用和队列持久化必须单独设计，不能把本地单用户状态直接当作多人服务实现。

## 6. Auto-Tune 生态架构

| 产品 | 核心用户 | 核心职责 | 与其他产品的关系 |
|---|---|---|---|
| Studio | 操作人员、算法工程师 | 单机数据分析、直接训练、LLM/HPO 调优、历史与报告 | 当前优先交付；沉淀稳定协议与训练核心 |
| Research | 科研人员、算法研究人员 | 可复现实验、训练配置对照、基础消融与实验报告 | 复用版本化协议和适配接口，不依赖 Studio UI 运行 |
| Cloud | 团队与组织 | 多用户、任务队列、算力调度、共享存储、权限与审计 | 消费稳定协议；不要求客户端先安装 Studio 或 Research |

三款产品共享品牌、概念模型、任务/数据/运行/指标协议和可复用算法组件，但必须可以分别安装、运行、测试和发布。不得通过直接复制 Studio 业务层或共享可变数据库来实现“复用”。

## 7. Research 轻量路线（暂不估时）

仅实施 R1：固定数据快照、模型、配置、随机种子与环境记录；围绕基线改变指定因素，顺序执行实验，支持停止、失败记录和恢复；输出指标、耗时、配置差异与最佳配置复用报告。复现要求为输入和执行配置可追溯，不承诺 GPU 结果逐位一致。

R1 仍须完成自动测试、最小真实训练、报告验收和文档回写；按艾卡最新要求暂不评估工期，也不计入工时合计。暂不安排模型缩放搜索、模块替换、结构搜索、自动读论文修改代码或新的 LLM 科研流程。R1 在 F1.2 完成后启动；不以未来研究扩展阻塞公司交付。

## 8. Cloud 分批路线（工程 45–75 人日，学习预留 15–25 人日）

范围限定为单台 Linux GPU 服务器、公司内部可信用户、CVAT 联合训练工作流和固定训练执行入口。以用户/项目权限隔离业务资源，不开放任意用户代码执行，不承诺面向不可信租户的强隔离。Cloud 首批规格必须定义 CVAT 项目、数据集版本、标注任务、训练任务、运行状态和模型产物的映射，以及双向触发、状态回写、失败重试和审计边界。

| 批次 | 主要范围 | 工程工作量 |
|---|---|---:|
| CL1 | CVAT 联合 API 契约、用户/项目映射、数据/任务/产物权限和审计 | 待 CVAT 规格后重估 |
| CL2 | 持久任务队列、独立 Worker、幂等、取消、心跳、失败恢复和 CVAT 状态回写 | 待 CVAT 规格后重估 |
| CL3 | 单机多 GPU 整卡分配、多任务并行、公平排队、资源释放与重启核对 | 8–13 人日 |
| CL4 | LLM 凭据管理、全局/用户并发与配额、超时退避、用量与证据隔离 | 7–12 人日 |
| CL5 | 受控单任务多卡训练、整组 GPU 预留、子进程失败与取消清理 | 6–10 人日 |
| CL6 | 部署、监控、压力与故障演练、真实多 GPU 验证、演示与文档 | 6–11 人日 |

GPU 训练队列与外部 LLM 请求额度分别治理；先完成 CVAT 联合 API 与状态闭环，再多任务分别占卡，最后验证单任务多卡。默认顺序 CL1→CL2→CL3→CL4→CL5→CL6。每批完成局部验收，CL6 做整体交付验证。

Studio F1.2 的单镜像单容器约束只适用于本地产品交付。Cloud 可独立部署 CVAT 适配 API、Worker 和持久服务；具体技术选型、新依赖、CVAT 版本与部署规格在立项时确认，复用稳定训练内核并保留原单机交付方式。

暂不做跨机器训练、集群编排、显存细粒度切分、商业计费、跨云容灾或高可用。须在 CL3/CL5 前取得至少两张兼容 GPU 的验证环境；模拟测试不能替代真实多 GPU 验收。
