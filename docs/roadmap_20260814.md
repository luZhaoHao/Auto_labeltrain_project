# Auto-Tune 生态产品路线图（2026-09-02 修订）

> 本文只维护产品边界、阶段顺序和长期约束。具体工作量与验收门槛见 `implementation_plan_20260814.md`；当前完成状态与下次开发入口见 `development_handoff_20260814.md`。

## 1. 路线结论

当前开发主线先收敛 Auto-Tune Studio，只完成两个正式任务：**YOLOv8 Detect** 与 **YOLOv8 Classify**。YOLOv5 Detect 不再开发。Auto-Tune Research 与 Auto-Tune Cloud 保留为后续独立产品线，但不插入本轮 Studio 交付顺序。

最终为用户提供三种彼此独立的训练策略：

1. **直接训练**：使用默认参数或用户明确填写的参数。
2. **HPO 调优**：使用确定性搜索流程产生并验证候选参数。
3. **LLM 调优**：基于代码生成的事实包提出受约束的参数建议。

三种策略共享数据快照、训练执行、状态、日志、历史和报告基础设施，但不串联决策。尤其不设计“HPO 结果再交给 LLM 判断”的流程；最终优胜结果按统一指标与确定性规则产生。

## 2. 当前产品边界

- 单用户、单机、离线优先，FastAPI + Jinja2，本地子进程执行训练。
- JSON/训练产物是事实来源，SQLite 用于索引和查询，不反向改写事实。
- 当前已具备 YOLOv8 Detect 的直接训练、可信 LLM 调优、审计、状态恢复、历史与报告闭环；Q1 已通过 Codex 独立验收，等待艾卡线下体验后提交发布。
- 当前稳定 Release 为 `v0.2`；后续开发以现有 S1、S2、P1–P5 验收基线为起点。
- 外部大模型服务是可选能力，不得成为直接训练或 HPO 的运行前提。

## 3. 后续阶段

| 阶段 | 目标 | 主要结果 | 预计工作量 |
|---|---|---|---:|
| Q1 | LLM 可信度最小闭环 | 事实包、严格 Schema、确定性校验、一次纠错、逐次审计、拒绝即不训练 | 已完成 |
| H1 | Detect HPO 最小业务线 | Optuna TPE、随机基线、固定预算、可恢复试验、确定性排名 | 6–10 人日 |
| C1 | Classify 直接训练闭环 | 数据接入、训练、Top-1/Top-5、状态、历史、报告与 UI | 7–12 人日 |
| C2 | Classify 调优能力 | Classify 专用事实包、LLM 约束、HPO 搜索空间与排名 | 4–7 人日 |
| F1 | 双任务冻结 | Detect/Classify 集成验收、兼容性与依赖事实同步 | 3–5 人日 |

**剩余合计：37–63 人日。** 该估算是单人有效研发工作量，不等同于自然日；不包含外部 GPU/资源准备等待、重大上游兼容问题和需求扩展。

## 4. 阶段依赖与顺序

`H1 Detect HPO → C1 Classify 直接训练 → C2 Classify 调优 → F1 双任务冻结 → S4 Windows/单 Docker 镜像/API 交付`

先在已稳定的 Detect 闭环上验证 LLM 可信度与 HPO 产品流程，可减少同时引入新任务和新调优机制的风险。Classify 先完成直接训练，再复用公共能力接入 LLM/HPO。

## 5. 关键技术决策

### 5.1 LLM 只负责受约束建议

- 事实由代码采集和计算，LLM 不生成事实。
- 输入事实带来源标识、缺失状态、数据类型和适用任务。
- 输出必须通过版本化 Schema；未知字段、非法类型、越界值和不适用参数直接拒绝。
- 业务校验器复核指标方向、参数依赖、当前值与建议值、运行状态和证据引用。
- 允许一次携带错误原因的纠错重试；仍失败则结束本轮，不启动训练。
- 最终排名、是否改善和停止条件由确定性代码计算，不由 LLM 自评。

### 5.2 HPO 采用 Optuna TPE

Optuna TPE 作为产品级 HPO 引擎，随机搜索作为基线；Ultralytics 内置遗传调优仅用于内部对照，不作为用户业务流程。原因是 Optuna 更适合统一管理 Detect/Classify 的试验、条件参数、持久化、恢复、预算和结果查询，也能继续复用现有训练执行与审计设施。

首版保持简单：小而明确的搜索空间、固定 trial 数、单目标指标、顺序执行；暂不引入 Ray、分布式搜索、多目标优化和激进剪枝。

### 5.3 两个任务共享基础设施，不共享任务语义

Detect 与 Classify 复用运行身份、子进程执行、状态机、日志、快照、历史、报告和 HPO 编排接口；各自维护数据校验、指标解析、事实画像、参数白名单、搜索空间和验收基线。禁止把 Detect 的指标或参数规则直接套用于 Classify。

## 6. Auto-Tune 生态架构

| 产品 | 核心用户 | 核心职责 | 与其他产品的关系 |
|---|---|---|---|
| Studio | 操作人员、算法工程师 | 单机数据分析、直接训练、LLM/HPO 调优、历史与报告 | 当前优先交付；沉淀稳定协议与训练核心 |
| Research | 科研人员、算法研究人员 | 可复现实验、结构/训练策略对照、消融与研究资产管理 | 复用版本化协议和适配接口，不依赖 Studio UI 运行 |
| Cloud | 团队与组织 | 多用户、任务队列、算力调度、共享存储、权限与审计 | 消费稳定协议；不要求客户端先安装 Studio 或 Research |

三款产品共享品牌、概念模型、任务/数据/运行/指标协议和可复用算法组件，但必须可以分别安装、运行、测试和发布。不得通过直接复制 Studio 业务层或共享可变数据库来实现“复用”。

## 7. Research 后续路线（建议 22–37 人日）

Research 定位为 **Studio 完成后的次要、实验性扩展线**，核心是复用 Studio 的训练、HPO、LLM 可信执行和试验管理基础，为研发人员提供可重复实验、自动消融和有限结构搜索，而不是建设完整 NAS 平台或“自主科学家”。

建议分层实施：

| 阶段 | 能力 | 工作量 |
|---|---|---:|
| R1 | 可重复实验与自动消融 | 6–10 人日 |
| R2 | depth/width/重复次数等模型缩放搜索 | 5–8 人日 |
| R3 | 注册模块替换与结构合法性校验 | 7–12 人日 |
| R4 | 集成、真实训练与研究报告 | 4–7 人日 |

Research 完整轻量路线合计 **22–37 人日**；若首版只完成 R1+R2，可控制在 **11–18 人日**。

可复用内容包括数据快照、Study/Trial、训练执行、状态、日志、失败恢复、Optuna、LLM 事实包/Schema/校验、指标解析、历史和报告。新增重点仅包括结构注册表、结构配置 Schema、模型构建/前向校验、参数量/FLOPs/延迟指标以及消融对比。

结构搜索只允许在注册表和有限结构空间内操作。LLM 不直接生成或修改 Python 模型源码；HPO/LLM 负责提出候选，结构合法性、训练执行和最终排名仍由确定性代码负责。

首版不做任意拓扑、DARTS/One-shot NAS、自动下载论文模块、开放式多 Agent 科研、多 GPU 大规模搜索或自主论文生成。

**近期决策：Research 暂停讨论、设计和立项，研发资源集中完成 Studio。** 仅在 Studio 双任务冻结、任务/指标/产物协议稳定后重新评估 Research。

## 8. Cloud 后续路线（建议 60–110 人日）

Cloud MVP 建议包含：用户与 RBAC、API 服务、持久任务队列、Worker、共享对象存储/数据库、基础 GPU 资源分配、租户隔离、审计、监控、失败恢复和 Studio 结果导入。首版不承诺复杂集群编排、计费系统、跨云容灾或企业级高可用。

该估算按可部署 MVP 计算，不包含生产级安全认证、等保/合规、复杂 Kubernetes 多集群和 7×24 运维体系。启动条件是 Studio 已完成 Windows、单 Docker 镜像与 API 交付且协议稳定。

## 9. 总体工作量视图

- Studio 剩余路线：37–63 人日。
- Research 轻量路线：22–37 人日；若首版仅 R1+R2，则为 11–18 人日。
- Cloud MVP：60–110 人日。
- Studio 剩余路线、Research 与 Cloud 合计：119–210 人日；这是顺序开发的有效研发工作量，不是交付承诺。

Research 与 Cloud 必须在各自立项时重新做需求确认、架构规格和风险评估，不能直接把上述区间拆成当前开发任务。

## 10. 当前不做

- YOLOv5 Detect 兼容与调优。
- HPO 与 LLM 串联裁决、多个 LLM 互审或复杂 Agent 图。
- 在 Studio 当前批次中建设 Ray Tune、分布式/多 GPU 调度或多租户平台。
- Segment、OBB、Pose 或其他新模型家族。
- 在双任务冻结前进行大规模架构重写。
