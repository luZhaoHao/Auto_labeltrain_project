# Auto-Tune 生态产品路线图（2026-09-16 修订）

## 2026-09-16 当前执行结论

H1.1、H1.2、H1.3 已完成实现、独立验证和人工体验确认，H1 Detect HPO 业务线验收结束。智能训练页面现已统一提供干运行预览、按原参数训练、HPO 算法调参和大模型调参；直接训练、HPO、LLM 三条真实训练路线均可完整执行。H1.3 最终证据见 [验收记录](h1_3_codex_review_20260916.md)。

当前不再设置 H1.4，后续顺序调整为：

`H1.3 已验收 → F1.1 产品优化与稳定版本冻结 → F1.2 Windows、Docker 与 API 交付适配 → R1 轻量 Research → Cloud 分批建设`

## F1.1 产品优化与稳定版本冻结

F1.1 不再扩展主体训练能力，而是对已完成系统进行查漏补缺、体验优化、效果专项和结构审计。范围包括三条真实训练路线的完整回归与失败恢复、LLM 加入事实推断后准确率下降的复现和修复、HPO 权重上传与少量常用权重预置、主操作按钮位置优化、轻量动态进度展示，以及对重复实现、职责混杂、超大文件和不必要依赖的证据化检查。

稳定化阶段不进行大规模重写。只有能够复现问题、具备回归测试并明确降低风险的结构调整才进入实现。F1.1 完成后冻结核心训练接口、运行身份、数据快照、产物和历史协议；后续原则上只接受阻断缺陷、安全问题和安装适配所必需的变化。

## F1.2 Windows Docker 与 API 交付适配

F1.2 在 F1.1 稳定基线上完成 Windows 安装、启动、配置、升级与卸载，以及单 Docker 镜像的 CPU/GPU 运行、健康检查和持久化目录验证。安装或容器化不得改变三条训练路线的业务语义，也不得把数据集、模型、密钥、日志或训练产物固化进安装包和镜像。

F1.2 同时达到可交付 API 基线：为数据分析、直接训练、HPO、LLM 调优、任务状态与日志、停止恢复、结果和受控产物查询提供稳定的版本化接口；统一请求响应 Schema、错误码、任务身份、幂等和最小访问边界；随 Windows 与 Docker 交付 OpenAPI 文档、健康检查、调用示例、接口烟测和端到端集成验证。Windows、Docker 和 API 三种入口必须复用同一业务内核并保持结果语义一致。

## 当前后置范围

Research 和 Cloud 不自动启动，也不作为当前稳定版本的前置条件。F1.2 只交付单用户受控 API，不包含公司平台深度改造、多人权限、持久队列或多 GPU 调度；这些继续作为后续独立范围，在 F1.2 完成后重新确认优先级与环境条件。

## 1. 路线结论

当前开发主线仅支持 **YOLOv8 Detect**。YOLOv5 Detect 不再开发。项目目标依次为：公司先能直接使用、通过统一 API 对接公司最新平台、形成可复现且有验证证据的工程项目。轻量 Research 保留，Cloud 作为多人、多 GPU、LLM 服务治理与权限并发的学习实践方向，在 Studio 交付后分批建设。

最终为用户提供三种彼此独立的训练策略：

1. **直接训练**：使用默认参数或用户明确填写的参数。
2. **HPO 调优**：使用确定性搜索流程产生并验证候选参数。
3. **LLM 调优**：基于代码生成的事实包提出受约束的参数建议。

三种策略共享数据快照、训练执行、状态、日志、历史和报告基础设施，但不串联决策。尤其不设计“HPO 结果再交给 LLM 判断”的流程；最终优胜结果按统一指标与确定性规则产生。

## 2. 当前产品边界

- 单用户、单机、离线优先，FastAPI + Jinja2，本地子进程执行训练。
- JSON/训练产物是事实来源，SQLite 用于索引和查询，不反向改写事实。
- 当前已具备 YOLOv8 Detect 的直接训练、HPO 调优、可信 LLM 调优、审计、状态恢复、历史与报告闭环；H1.3 已于 2026-09-16 完成独立验证和艾卡人工体验确认。
- 当前稳定 Release 为 `v0.2`；后续开发以现有 S1、S2、P1–P5 验收基线为起点。
- 外部大模型服务是可选能力，不得成为直接训练或 HPO 的运行前提。

## 5. 关键技术决策

### 5.1 LLM 只负责受约束建议

- 事实由代码采集和计算，LLM 不生成事实。
- 输入事实带来源标识、缺失状态、数据类型和适用任务。
- 输出必须通过版本化 Schema；未知字段、非法类型、越界值和不适用参数直接拒绝。
- 业务校验器复核指标方向、参数依赖、当前值与建议值、运行状态和证据引用。
- 允许一次携带错误原因的纠错重试；仍失败则结束本轮，不启动训练。
- 最终排名、是否改善和停止条件由确定性代码计算，不由 LLM 自评。

### 5.2 HPO 采用 Optuna TPE

Optuna TPE 作为产品级 HPO 引擎，随机搜索作为基线；Ultralytics 内置遗传调优仅用于内部对照，不作为用户业务流程。原因是 Optuna 更适合管理 Detect 的试验、条件参数、持久化、恢复、预算和结果查询，也能继续复用现有训练执行与审计设施。

首版保持简单：小而明确的搜索空间、固定 trial 数、单目标指标、顺序执行；暂不引入 Ray、分布式搜索、多目标优化和激进剪枝。

### 5.3 复用训练核心与版本化协议

Studio、Research 与 Cloud 复用运行身份、训练执行、指标、数据快照和产物协议。研究实验与云端调度各自维护编排逻辑；不为未规划任务提前建设适配框架。Cloud 的任务权限、资源占用和队列持久化必须单独设计，不能把本地单用户状态直接当作多人服务实现。

## 6. Auto-Tune 生态架构

| 产品 | 核心用户 | 核心职责 | 与其他产品的关系 |
|---|---|---|---|
| Studio | 操作人员、算法工程师 | 单机数据分析、直接训练、LLM/HPO 调优、历史与报告 | 当前优先交付；沉淀稳定协议与训练核心 |
| Research | 科研人员、算法研究人员 | 可复现实验、训练配置对照、基础消融与实验报告 | 复用版本化协议和适配接口，不依赖 Studio UI 运行 |
| Cloud | 团队与组织 | 多用户、任务队列、算力调度、共享存储、权限与审计 | 消费稳定协议；不要求客户端先安装 Studio 或 Research |

三款产品共享品牌、概念模型、任务/数据/运行/指标协议和可复用算法组件，但必须可以分别安装、运行、测试和发布。不得通过直接复制 Studio 业务层或共享可变数据库来实现“复用”。

## 7. Research 轻量路线（暂不估时）

仅实施 R1：固定数据快照、模型、配置、随机种子与环境记录；围绕基线改变指定因素，顺序执行实验，支持停止、失败记录和恢复；输出指标、耗时、配置差异与最佳配置复用报告。复现要求为输入和执行配置可追溯，不承诺 GPU 结果逐位一致。

R1 仍须完成自动测试、最小真实训练、报告验收和文档回写；按艾卡最新要求暂不评估工期，也不计入工时合计。暂不安排模型缩放搜索、模块替换、结构搜索、自动读论文修改代码或新的 LLM 科研流程。R1 在 S4 完成后启动；不以未来研究扩展阻塞公司交付。

## 8. Cloud 分批路线（工程 45–75 人日，学习预留 15–25 人日）

范围限定为单台 Linux GPU 服务器、公司内部可信用户、固定训练执行入口。以用户/项目权限隔离业务资源，不开放任意用户代码执行，不承诺面向不可信租户的强隔离。

| 批次 | 主要范围 | 工程工作量 |
|---|---|---:|
| CL1 | 用户/项目 RBAC、平台身份映射、数据/任务/产物访问权限和审计 | 8–13 人日 |
| CL2 | 持久任务队列、独立 Worker、幂等、取消、心跳、失败恢复和并发上限 | 10–16 人日 |
| CL3 | 单机多 GPU 整卡分配、多任务并行、公平排队、资源释放与重启核对 | 8–13 人日 |
| CL4 | LLM 凭据管理、全局/用户并发与配额、超时退避、用量与证据隔离 | 7–12 人日 |
| CL5 | 受控单任务多卡训练、整组 GPU 预留、子进程失败与取消清理 | 6–10 人日 |
| CL6 | 部署、监控、压力与故障演练、真实多 GPU 验证、演示与文档 | 6–11 人日 |

GPU 训练队列与外部 LLM 请求额度分别治理；先多任务分别占卡，再单任务多卡。默认顺序 CL1→CL2→CL3→CL4→CL5→CL6。每批完成局部验收，CL6 做整体交付验证。

Studio S4 的单镜像单容器约束只适用于 Studio/Engine 交付。Cloud 可独立部署 API、Worker 和持久服务；具体技术选型、新依赖和部署规格在立项时确认，复用版本化接口，保留原单机交付方式。

暂不做跨机器训练、集群编排、显存细粒度切分、商业计费、跨云容灾或高可用。须在 CL3/CL5 前取得至少两张兼容 GPU 的验证环境；模拟测试不能替代真实多 GPU 验收。

旧版 Studio 为 37–63 人日，新版为 26–44 人日，减少 11–19 人日（对应区间端点约 30%）。Studio 保留原冻结和封装预算，未重复扣减验收成本。Research 暂不估时，Cloud 范围也已重定，因此不再比较整项目节省比例。

仅对已估算的 Studio + Cloud：按每周 5 个有效研发日，含学习预留约 18–29 周；每周 3 个有效日约 29–48 周。这不含 Research、资源采购申请、平台联调等待、日常业务打断和重大兼容问题，不代表完整项目交付周期。

学习预留用于队列/权限、GPU 调度与多卡、LLM 治理的原型、阅读和返工，不替代各批次工程验收。Cloud 可信度低于 Studio，需在 CL1 规格确认及 CL3 技术验证后重新估算。简历和演示只使用实际实现及测量结果，不预写并发规模、吞吐量或可靠性成果。

## 10. 当前不做

- YOLOv5 Detect 兼容与调优。
