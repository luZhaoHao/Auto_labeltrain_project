# 项目路线规划（2026-08-14）

> 本文档维护 Auto-Tune 的产品方向和阶段路线。当前版本与下次开发注意事项见 `docs/development_handoff_20260814.md`。

## 1. 项目现状

> 2026-08-14 状态：A0 审计闭环与统一训练收尾已完成并发布为 `v0.1`；后续任务顺序见 `docs/implementation_plan_20260814.md`。

### 1.1 已完成
- **Module A（数据集分析器）**：图像质量（模糊/曝光/SNR）、bbox 几何、类别分布、特征聚类。经 3 个真实数据集验证。
- **Module B（训练结果分析器）**：三阶段诊断（指标摘要 → DeepSeek 文本诊断 → Qwen-VL 视觉分析），34 项测试通过。
- **Module C（自动调优 Agent）**：感知 → LLM 决策 → Guardrails → 执行 → 探针监控，自动调参 Loop 完成。
- **Web UI**：完整工作流（上传/选路径 → 分析 → 划分 → 训练 SSE 监控 → 看结果 → 保存报告），SPA 单页 5 Tab，中英 i18n。
- **最佳迭代追踪**：综合评分选最优迭代、保存报告。

### 1.2 技术栈与现状约束
- 后端：FastAPI + Jinja2；存储：JSON 文件（`log/` 平铺）+ subprocess 启动 YOLO 训练 + SSE 流式。
- **单用户、单机、无数据库、无用户体系、单目录存储**。
- 配置源：`config.yaml`（含 llm/vision/guardrails/probe/dataset_analyzer/train_analyzer/training 段）。

## 2. 核心目标

- **本地单机部署与在线多人平台两者都做**；在线是本地功能的拓展（核心分析代码一份，多用户层叠加）。
- 新增能力方向：任务类型扩展（分类/分割/OBB）、YOLO 版本（v5/v11/v26）、非超参数调优维度（损失策略/推理阈值）、模型架构实验平台、在线多人平台。

## 4. 关键决策与依据

### 4.1 分层架构（本地与在线共存）

```
核心层（复用，无需改动）：Module A/B/C 分析逻辑 + executor + SSE 流式
数据层（重构）：JSON 平铺  →  SQLite + 按用户分目录
接入层（新增）：用户认证 + 数据隔离 + 训练队列/GPU 调度
UI 层（拓展）：登录页 + 个人空间 + 队列状态
```

本地部署 = 单用户模式（跳过认证层，数据走默认目录）；在线 = 开启多用户层。核心分析代码一份，两处共享。

### 4.2 在线平台范围与估算

| 模块 | 工作量 |
|------|--------|
| 用户体系（注册/登录/角色） | 2-3 天 |
| 数据隔离（按用户分目录） | 2-3 天 |
| 训练任务队列 + GPU 并发调度 | 3-5 天（难点） |
| SQLite 数据库 | 2-3 天 |
| 前端适配 + 安全加固 | 2-4 天 |
| **合计** | **约 11-18 天** |

现状约束：无用户体系、无数据库、单目录 JSON 存储、本地 subprocess 训练、SSE 单会话。

### 4.3 CVAT 融合调研（Phase 2 在线标注）

- CVAT 现状：Django + PostgreSQL + Redis + **17 个 Docker 容器** + React。已具备项目/任务/标注/数据集导出/组织权限/异步队列/自动标注；**缺训练调度**。
- **完全糅合为一个代码库不可行**（技术栈完全不同，数周 + 高风险）。
- **可行的是路线 B 解耦集成**：`cvat-develop/` 内现成《CVAT_YOLOv8训练功能设计方案.docx》明确推荐"已有成熟训练软件优先解耦"——**Auto-Tune 即该成熟训练软件**。
  - 集成点：① CVAT 导出 → Auto-Tune 分析/训练（1-2 天）；② 模型回传 → CVAT 自动标注（2-3 天）；③ token 鉴权（3-5 天）；④ **训练队列 + GPU 调度仍需自写（3-5 天，省不掉）**。
  - 耦合总工程量约 **12-19 天，与自建（11-18 天）相当**；难点分布不同：自建重在自己代码，耦合重在学 Django/17 容器运维。
  - Auto-Tune Module A 能力覆盖设计文档第 6 节"数据质量审查"需求。
- 文档入口：`cvat-develop/CVAT_YOLOv8训练功能设计方案.docx`（已提取文本到 `Auto_labeltrain_project/cvat_yolov8_design.md`）。

### 4.4 任务类型与 YOLO 版本扩展

- **yolo11/yolo26**：同 `yolo train` CLI + 同 results.csv 列，只加模型文件 + UI 模型列表 + ultralytics 升级。**最优先**。
- **分割 / OBB**：目录结构、data.yaml、mAP 指标列与检测**完全相同**，Module B/C 几乎零改动；主要改 Module A 标签解析（分割=多边形变长行，OBB=6 值含角度）。分割 2-3 天、OBB 1-2 天。
- **yolov5**：独立仓库 `python train.py`，results.csv 列不同（`mAP@0.5` / `obj_loss`），需改 executor 命令构造 + 指标列映射。2-3 天。
- **分类**：全链路不同（目录按类分文件夹、data.yaml 用 list、metrics 为 accuracy_top1/top5、评分公式重写）。3-4 天。

### 4.5 模型架构实验平台（优先级最后）

- 用户目标：超参数以外的架构拓展——Backbone 革新 / Neck 增强 / Attention 即插即用 / 卷积算子魔改 / Loss 优化，专为**研究方向**。
- 可行性：**可行**。ultralytics 天生模块化（模型结构由 yaml 描述，自定义模块注册后即可引用，训练用 `model=自定义.yaml`）。
- 工程量 **8-15 天**：模块库 3-5 + 结构生成器 2-3 + executor yaml 训练 1-2 + 决策层动作空间 2-3 + UI 实验记录 1-2。
- 关键风险：改结构难加载预训练权重；模块与 ultralytics 版本耦合；LLM 自由选结构不可靠。
- 推荐做法：**预设变体模板 + 有限组合**，Agent 自动跑消融实验（baseline vs +CBAM vs +BiFPN），实验与生产分离。

## 5. 路线图

```
阶段 A0：当前闭环可靠性加固（4-7 天）
  ① Module B 事实层与配置阈值修复
  ② 超参数注册表 + LLM Schema + Guardrails 唯一执行值
  ③ 执行审计、启动可靠性、上传安全与 UI 结果同步

阶段 A：本地基础（2-3 天）
  ① yolo11/yolo26 + task/version 配置框架    ← 共用底座
  ② Linux 迁移                               ← 在线部署前提
  ③ 拖拽上传（顺手 0.5 天）

阶段 B：在线平台 Phase 1（11-18 天）——以多用户最终形态一次性落地
  用户体系 + SQLite + 数据隔离 + 训练队列/GPU 并发
  + 多数据集 + 历史记录 + SSE 恢复
  （核心层复用，数据/接入层重构）

阶段 C：后置（按需穿插，约 15-25 天）
  优化 LLM 分析 → 一键分析 → 任务类型扩展 → yolov5 → 模型架构实验平台 → 在线标注 Phase 2（CVAT）
```

## 6. 待审核焦点（Codex 重点分析）

1. **取舍是否合理**：并入在线平台的 5 项（SQLite/多数据集/历史记录/SSE 重连/一键分析）是否确实会被重构而非可独立交付？
2. **阶段顺序**：yolo11/26 是否真为最佳起点？阶段 A → B → C 的顺序有无更优安排？
3. **分层架构**：核心层复用 + 数据/接入层重构是否可行？有无更优方案（如直接以在线架构起步）？
4. **工作量估算**：在线平台 11-18 天是否靠谱？训练队列/GPU 并发调度难点是否被低估？
5. **CVAT 路线**：解耦集成（路线 B）是否最优？在线平台 Phase 1 是否该现在就为 CVAT 集成做架构预留（如任务/模型 API 设计）？
6. **任务扩展优先级**：yolo11/26 > 分割 > OBB > yolov5/分类 的排序是否合理？
7. **风险遗漏**：多用户数据隔离漏洞、GPU 资源竞争、部署运维、训练进程/重启恢复、上传安全等是否有遗漏？
8. **资源冲突**：模型架构实验平台与在线平台是否存在顺序/资源矛盾？
