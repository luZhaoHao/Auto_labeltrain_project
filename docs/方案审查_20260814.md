# Auto-Tune 后续实施方案审查（2026-08-14）

## 一、审查结论

现有 `roadmap_20260814.md` 和 `implementation_plan_20260814.md` 的产品方向基本正确：保留本地单机能力，以 Module A/B/C 为业务核心，后续增加在线多人平台、任务类型、YOLO 版本、模型结构实验和 CVAT 集成。

需要调整的核心判断是：**Module A/B/C 不是“无需改动的核心层”，而是“理念可复用、接口需要先加固的核心域”**。在继续 YOLO 版本扩展或在线化之前，应增加阶段 A0，修复事实层、参数决策、安全护栏、实际执行和实验审计之间的不一致。

推荐总顺序：

```text
A0 当前闭环可靠性加固
→ A1 task/version 适配框架
→ A2 Linux 与部署基线
→ A3 上传及本地体验
→ B 在线多人平台
→ C1 任务类型扩展
→ C2 模型结构解析与受控结构自调整
→ C3 CVAT 深度集成
```

## 二、现有方案中合理的部分

1. Module A 使用传统 CV 产生结构化事实，成本可控。
2. Module B 采用“代码读数、规则诊断、LLM解释、视觉按需”的三阶段设计。
3. Module C 采用“感知—决策—护栏—执行—探针—复盘”的闭环。
4. 本地与在线共用业务核心、在线增加认证/隔离/调度层的总体思路合理。
5. CVAT 与训练系统采用解耦 API 集成优于直接揉合代码库。
6. 模型结构实验使用预设模板和有限组合，优于让 LLM 任意生成模型结构。
7. 分类、分割、OBB、YOLOv5 应按实际业务需求逐项适配，而不是一次性泛化。

## 三、必须修正的判断

### 3.1 阶段 A 缺少可靠性加固

当前已确认的问题包括：

- Guardrails 的截断值未成为唯一执行值；
- `training_overrides` 可绕过首轮校验；
- `optimizer=auto` 会使 `lr0`/`momentum` 建议失效；
- Prompt、Guardrails 和 CLI 映射的参数集合不一致；
- Module B 自定义阈值可能因配置层级错误而失效；
- Early Stopping 和 Stale 检测路径不完整；
- 调优历史没有可靠的 before/after/delta；
- Module C 缺少正式 pytest 覆盖；
- 普通训练完成后 UI 没有回填指标、生成历史和自动衔接分析；
- Windows 启动方式依赖 PATH 中的裸 `yolo` 命令。

这些问题会直接污染后续在线平台、任务扩展和结构实验的数据可信度，因此必须作为 A0 先修复。

### 3.2 YOLO11/26 不应早于 A0

版本适配是必要底座，但它解决的是“能否训练不同版本”，不是“系统是否可靠采用 AI 建议”。如果先扩版本，会把现有参数语义和执行问题扩散到更多适配器。

此外，YOLO26 必须先验证当前 Ultralytics 版本、官方模型名称、权重格式和指标列，不应仅靠增加下拉选项完成。

### 3.3 在线平台 11–18 天偏乐观

若只做内部演示原型，该估算可能成立；若要求多人稳定使用，需要补充：

- 任务幂等与数据库迁移；
- Web 与训练 Worker 分离；
- GPU 原子租约和显存策略；
- 服务重启后的进程/Checkpoint 对账；
- 孤儿进程与取消语义；
- 上传限额、压缩炸弹、路径穿越；
- 用户磁盘配额和产物生命周期；
- SSE 事件持久化、游标和重放；
- 权限越权测试、备份和恢复。

建议内部可用版本按 3–5 周评估，生产化另行增加稳定性周期。

### 3.4 SQLite/历史记录不应全部推迟

不建议现在完整建设多人数据库，但应立即稳定领域接口：

```text
DatasetRepository
TrainingJobRepository
ReportRepository
ArtifactStore
TuningAuditRecord
```

一期仍可落到 JSON；阶段 B 将实现替换为 SQLite/PostgreSQL，而不改变业务对象含义。

### 3.5 模型结构解析与结构自调整应作为同一期独立子项目

用户目标已经明确：当前一期只调超参数；后续一期同时完成结构解析和受控结构调整。该阶段应独立于普通超参数闭环，避免无法判断收益来源。

结构阶段只允许：

- 解析模型 YAML、Backbone、Neck、Head、Stride、参数量和 FLOPs；
- 从已注册的模块库选择有限变体；
- baseline 与单变量/小组合消融；
- 兼容性预检和显存预算；
- 训练失败自动回退到合法 baseline。

不得允许 LLM 执行任意 Python、任意 YAML 标签或任意模块导入。

## 四、风险优先级

| 级别 | 风险 | 处理阶段 |
|---|---|---|
| P0 | 明文 API 密钥、ZIP 路径穿越 | A0 |
| P0 | Guardrails 调整值未用于实际训练 | A0 |
| P1 | Module B 事实错误导致 LLM 错误决策 | A0 |
| P1 | 参数显示值与 Ultralytics 实际值不一致 | A0 |
| P1 | 数据划分移动原始文件、缺少不可变快照 | A0/B |
| P1 | 单进程全局训练状态无法在线化 | B |
| P1 | GPU 双分配、孤儿进程、重启恢复 | B |
| P2 | UI 日志过载、指标不回填、历史不完整 | A0/A3 |
| P2 | 多任务/多版本指标字段差异 | A1/C1 |
| P2 | 结构变体与预训练权重不兼容 | C2 |

## 五、阶段验收原则

每个阶段必须同时满足：

1. 自动测试通过；
2. 关键操作有失败路径测试；
3. UI、报告、审计记录和实际执行参数一致；
4. 产物能够追溯到数据快照、代码/配置版本和训练任务；
5. 新功能不破坏现有 YOLOv8 Detect 本地流程。
