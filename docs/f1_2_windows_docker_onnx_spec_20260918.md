# F1.2 Windows Docker 与 ONNX 模型导出规格

状态：已确认并完成 F1.2-A 至 F1.2-D 实现与独立验收；F1.2-E 联合验收关键路径通过，等待手册截图、最终发布包和发布确认。

## 1. 结论

F1.2 交付一个完整的 Auto Tune Studio 产品，分别提供 Windows 便携安装和单 Docker 镜像两种运行方式。用户通过 Web 界面完成所有操作，不提供、不宣传也不要求调用外部 API。F1.2 同时增加独立的 PT 转 ONNX 手动导出通道。

统一任务 API、队列、权限、幂等、日志与产物调度不属于 F1.2，后移到 Cloud，并与 CVAT 项目、数据集、标注任务、训练触发、状态回写和模型产物回传共同设计。

原预计工作量为 **8–15 人日，约 2–3 个工作周**。截至 2026-09-24，A 至 D 已完成，E 的代码与两种交付关键路径已联合复验；剩余时间主要取决于截图准备、DOCX 排版复核和最终发布包构建。

## 2. 产品边界

### 2.1 F1.2 必须交付

- Windows 便携安装、启动、配置、升级、卸载和数据保留。
- 一个 `auto-tune` Docker 镜像和一个容器，运行完整 Studio Web UI。
- Docker 正常启动即申请 NVIDIA GPU，验证 Studio 与 GPU 训练、健康检查、目录挂载和容器重启后的数据保留；不交付 CPU 训练或无 GPU 运行模式。
- Windows 与 Docker 复用同一套配置、目录初始化、健康检查和持久化规则。
- 独立 PT 转 ONNX 手动导出入口。
- 自动化测试、Docker/Windows 集成验证、最小真实训练和 ONNX 最小推理验证。
- F1.2 功能稳定后编写软件安装手册。
- F1.2 最终验收前，由艾卡补充软件操作手册与软件安装手册截图；Codex 完成内容和排版核对。

### 2.2 F1.2 不做

- `/api/v1/jobs` 或其他外部任务 API。
- 仅 API 的 Engine 模式。
- CVAT 联动、公司平台调度、多人权限、持久队列或多 GPU 调度。
- Linux 原生安装包、Python Wheel、第二个 Docker 镜像或 Web/Worker 多容器拆分。
- 自动转换每次训练的权重。
- 改写直接训练、HPO、LLM 调优的核心业务协议。

现有页面内部 HTTP 请求仅属于 Studio 实现细节，不形成对外兼容承诺。容器可以保留不面向普通用户的健康检查入口。

## 3. 总体架构

### 3.1 单产品双交付

Windows 和 Docker 都启动同一个 FastAPI + Jinja2 Studio，不维护第二套业务实现。共享交付层只处理以下事项：

- 读取启动地址、端口和配置文件位置。
- 初始化持久化目录。
- 校验配置、目录写入权限和运行依赖。
- 提供健康检查。
- 保持日志、SQLite、训练结果、模型和配置在升级或重启后可用。

Docker 专属层只处理 Linux 容器、镜像依赖、挂载和 NVIDIA Runtime。Windows 专属层只处理便携环境、启动脚本、升级、卸载和快捷入口。

### 3.2 Docker 推荐基线

- 容器类型：Linux 容器，通过 Docker Desktop WSL2 运行。
- 推荐基础镜像：`nvidia/cuda:12.1.1-cudnn8-runtime-ubuntu22.04`。
- Python：3.10。
- PyTorch：2.5.1 CUDA 12.1 wheel；正式 Docker 启动配置必须申请 GPU。GPU 不可用时明确报错，不静默回退到 CPU。
- 服务监听：容器内 `0.0.0.0:8000`，宿主机默认映射 `127.0.0.1:8000`。
- 容器内工作目录：`/opt/auto-tune`。
- 数据集挂载：`/data/datasets`。
- 持久化挂载：配置、`log/`、`detect/`、`runs/` 和 `models/weights/`。
- 镜像不得包含真实 `config.yaml`、API 密钥、数据集、权重、日志或训练结果。

如果推荐 CUDA 基线与实际 RTX 3060 Laptop GPU 驱动不兼容，实施者必须提供驱动、CUDA、PyTorch 三者的证据，再调整版本；不得改用未固定的 `latest` 镜像。

## 4. PT 转 ONNX 通道

### 4.1 入口位置

F1.2-A 只保留“上传权重文件后导出 ONNX”的路径。导出入口放在现有受控权重库的上传区域：用户上传 `.pt`，在同一权重库选择该模型并点击“导出 ONNX”。不从训练结果、历史记录或任意服务器路径直接选择模型，也不在直接训练、HPO 和 LLM 调优页面分别实现转换功能。

### 4.2 用户流程

1. 用户将可信 `.pt` 上传到现有受控权重库。
2. 用户在权重库选择已上传模型；兼容来源的只读权重不提供导出按钮。
3. 页面默认只显示“导出 ONNX”（FP32）；展开“高级选项”后可选择 FP16，其他导出参数沿用当前稳定默认值。
4. 用户主动点击导出，页面显示导出中、完成或失败状态，重复点击不能并发启动同一导出。
5. 完成后在同一权重条目提供 ONNX 下载。

### 4.3 默认参数与安全约束

- 固定 `imgsz=640`、`opset=17`、`dynamic=False`、`simplify=False`、`nms=False`；首批不开放这些参数的页面输入。
- 高级选项中的导出精度默认 `FP32`；FP16 只有在当前依赖和最小推理实测通过后才开放。FP16 是半精度导出，不把它描述成 INT8 量化。
- 首批不提供 INT8。INT8 静态量化需要代表性校准数据，与“只上传权重即可转换”的产品范围冲突；动态 INT8 对 YOLO 卷积模型收益和兼容性不足，不能用未经验证的选项代替正确校准。
- 客户端不能提交任意服务器路径，只能提交现有受控权重库公开的 `model_id`，且仅允许 `origin=managed` 的上传权重。
- FP32 输出固定写入上传权重同目录，文件名为 `<stem>.onnx`；FP16 输出为 `<stem>.fp16.onnx`。用户不选择导出目录。
- 若目标文件已存在，返回稳定冲突，不提供覆盖入口；确需重导出时，由用户使用不同文件名重新上传权重。
- 完成响应提供文件名、大小、来源 `model_id`、精度和下载入口；失败只返回稳定错误码和提示，不暴露服务器路径或异常堆栈。首批不新增数据库或持久任务队列。
- 导出失败不得改变原训练、HPO 或 LLM 调优的终态。

### 4.4 验收

- 至少上传一个真实可信 `.pt` 并完成 FP32 ONNX 导出；具备兼容 GPU 时再验证 FP16。
- ONNX 结构检查通过。
- 使用固定样例完成 PyTorch 与 ONNX 最小推理，输出形状一致；数值容差在编码前计划中冻结。
- 非法来源、兼容只读来源、缺失或被替换模型、不支持参数、重复提交和目标冲突均有稳定错误码，不泄露路径，不静默覆盖已有导出文件。
- 上传本身继续把 `.pt` 当作不透明字节；只有用户明确确认“权重来源可信”并发起导出时才加载模型。导出加载在独立子进程中运行，失败或崩溃不得拖垮 Studio 主进程。

F1.2-A 编码前核对当前 Conda 环境和交付依赖；如需新增依赖，先列出包名、固定版本、体积和用途，取得艾卡确认。当前环境目录可见 `onnx 1.17.0`、`onnxruntime-gpu 1.22.0`、`onnxslim 0.1.94`、`ultralytics 8.3.253`，但尚未运行解释器确认导入与导出可用。

## 8. 当前已知前置风险

- F1.2-A 会从“上传时不反序列化”进入“导出时加载可信权重”；必须增加明确确认、子进程隔离和安全测试，不能把任意上传文件直接加载到 Studio 主进程。
- 当前 ONNX、ONNX Runtime 或简化依赖是否完整尚未验证；新增依赖必须在 F1.2-A 规格确认后固定版本。
- 当前机器已安装 Docker CLI，但 2026-09-18 检查时 Docker Desktop Linux Engine 未启动；该问题顺延为 F1.2-B 前置条件，不阻塞 F1.2-A。
- 当前项目大量运行路径依赖工作目录下的 `log/`、`detect/`、`runs/` 与配置文件，Docker 第一批必须验证挂载和工作目录，不能只验证页面能打开。
- 当前依赖清单存在根目录、`auto_tune/requirements.txt` 和 `environment.yml` 多份版本；Docker 必须建立受控运行依赖清单，不能直接混装三份依赖。
- ONNX 依赖虽已出现在当前 Conda 环境目录，仍须实测导入、实际导出及 Windows/Docker 后续交付依赖；不能以目录存在代替验收。
