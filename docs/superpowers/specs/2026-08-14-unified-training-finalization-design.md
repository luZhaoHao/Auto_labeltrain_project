# 普通训练与自动调优统一收尾设计

**日期：** 2026-08-14  
**阶段：** A0.2 第 2 项  
**状态：** 待用户确认后进入实施计划

## 1. 目标

在不改变自动调优安全闭环的前提下，让普通训练与自动调优训练共享同一套训练完成收尾、Module B 分析、KPI 提取、实验历史和界面展示逻辑。

完成后，用户从界面看到的两类训练都属于统一的“训练实验”，以来源字段区分；自动调优仍保留 LLM 决策、Guardrails、探针、重试和审计等专属能力。

## 2. 范围

### 2.1 本批包含

1. 抽取可复用的训练完成收尾服务。
2. 普通训练成功后自动执行 Module B 分析并回填 KPI。
3. 自动调优训练完成后复用同一收尾服务。
4. 新增统一实验历史并支持原子写入、幂等更新和旧数据兼容。
5. 统一普通训练与自动调优的完成结果结构。
6. 调整训练监控、训练历史和历史详情界面。
7. 增加后端、SSE、历史存储和 UI 回归测试。

### 2.2 本批不包含

1. 不建设数据库、用户体系、任务队列或 GPU 调度。
2. 不统一普通训练与自动调优的控制流程；自动调优继续独立执行决策、护栏和探针。
3. 不修改模型结构，不增加模型结构自调整。
4. 不进行整体 UI 改版，不改变导航和视觉主题。
5. 不处理 Linux 迁移、YOLO11/26、多任务训练或不可变数据快照。
6. 不新增第三方依赖。
7. 不实现 SSE 断线恢复或服务器重启后的训练任务接管；该能力保留到阶段 B4。

## 3. 方案选择

采用“共享收尾服务”方案：两类训练保留各自的启动与控制逻辑，在训练结束后汇入同一个收尾入口。

不采用在 `app.py` 中直接复制分析代码的最小方案，因为它会继续扩大普通训练与调优训练之间的行为差异；也不提前引入数据库任务系统，因为这属于阶段 B。

## 4. 架构设计

### 4.1 统一收尾服务

新增独立模块，建议位置：

`auto_tune/modules/train_analyzer/training_finalizer.py`

服务接收：

- `run_dir`：训练产物目录；
- `run_name`：训练名称；
- `source`：`manual` 或 `tuning`；
- `config`：分析配置；
- `log_dir`：报告与历史目录；
- `training_status`：`completed`、`failed` 或 `cancelled`；
- 可选的 `session_id`、`audit_path`、开始时间和结束时间。

服务负责：

1. 校验训练目录和基础产物。
2. 使用现有 `results_parser`、曲线分析、问题检测和运行比较模块生成 Module B 报告。
3. 提取统一 KPI。
4. 原子保存报告。
5. 构造统一完成结果。
6. 幂等写入统一实验历史。

服务不得负责启动训练、调用 LLM、执行 Guardrails、监控探针或决定是否重试。

### 4.2 统一完成结果

普通训练 SSE 和自动调优收尾至少共享以下结构：

```json
{
  "run_id": "manual:train39",
  "run_name": "train39",
  "source": "manual",
  "status": "completed",
  "analysis_status": "completed",
  "started_at": "2026-08-14T00:00:00Z",
  "finished_at": "2026-08-14T00:01:00Z",
  "params": {},
  "metrics": {
    "mAP50": 0.0,
    "mAP50_95": 0.0,
    "precision": 0.0,
    "recall": 0.0
  },
  "epochs": {
    "configured": 1,
    "completed": 1,
    "best": 1
  },
  "artifacts": {
    "run_dir": "detect/train39",
    "report_path": "log/train39_report.json",
    "audit_path": null
  },
  "error": null,
  "analysis_error": null
}
```

缺失指标保持缺失，真实零值必须保留。路径字段保存实际可追溯路径，不伪造不存在的产物。

### 4.3 状态语义

训练状态与分析状态分离：

- 训练成功、分析成功：`status=completed`，`analysis_status=completed`。
- 训练成功、分析失败：`status=completed`，`analysis_status=failed`。
- 训练失败：`status=failed`，`analysis_status=skipped`。
- 用户取消：`status=cancelled`，`analysis_status=skipped`。

分析失败不得覆盖已经成立的训练成功事实。所有错误采用结构化对象，至少包含 `stage`、`error_type`、`message` 和 `timestamp`。

## 5. 统一实验历史

新增：

`log/experiment_history.json`

该文件是 UI 的统一历史事实源，包含普通训练与自动调优训练。每条记录使用稳定 `run_id`：

- 普通训练：`manual:<run_name>`；
- 自动调优：`tuning:<session_id>:<run_name>`。

写入要求：

1. 使用临时文件加 `os.replace` 原子更新。
2. 相同 `run_id` 重复收尾时更新原记录，不追加重复项。
3. 写入失败不能破坏旧历史。
4. 记录按完成时间排序。
5. 历史文件使用版本化顶层结构，例如 `schema_version` 与 `experiments`。

原 `tuning_history.json` 暂时保留，继续作为 LLM 获取上一轮调参反馈的内部数据源。普通训练不得写入该文件，避免污染调参决策。

### 5.1 旧历史兼容

读取统一历史时兼容现有 `tuning_history.json`：

1. 将可识别的旧调优记录映射为 `source=tuning` 的只读兼容记录。
2. 使用稳定 ID 去重；新实验历史中已存在同一训练时，不再显示旧记录。
3. 不删除、不覆盖原 `tuning_history.json`。
4. 无法完整映射的字段保持缺失，不补虚假默认值。

## 6. 两条训练链路的接入

### 6.1 普通训练

`/api/training/start` 在进程结束后调用统一收尾服务：

- return code 为 0：执行 Module B 分析，SSE 返回统一结果。
- return code 非 0：写入失败实验历史，不执行完整分析。

普通训练现有参数和命令构造本批不做大范围重构，但完成结果不得再只依赖临时的 `_build_training_result_payload()`。

### 6.2 自动调优

自动调优在完整训练结束后调用同一收尾服务，并把返回的 KPI 写入：

- 当前迭代结果；
- A0 审计记录的 `after_metrics` 与 `metric_delta`；
- 统一实验历史。

自动调优审计仍由 `TuningAuditSession` 负责，统一收尾服务只保存其 `audit_path`，不修改审计状态机。

## 7. UI 设计

### 7.1 训练监控完成区

普通训练完成后展示：

- 训练状态与分析状态；
- mAP50、mAP50-95、Precision、Recall；
- 已完成 epoch 与 best epoch；
- 查看训练分析或训练目录的入口。

训练成功但分析失败时使用警告样式，文案明确为“训练完成，结果分析失败”，不能显示成训练失败。

### 7.2 训练历史页

统一表格展示：

- 来源；
- 训练名称；
- 模型；
- 数据集；
- 训练状态；
- 分析状态；
- 四项 KPI；
- 完成时间；
- 详情入口。

提供轻量筛选：

- 来源：全部、普通训练、自动调优；
- 状态：全部、成功、失败、取消。

### 7.3 历史详情

公共区域显示参数、KPI、epoch、产物路径和错误。

当 `source=tuning` 时额外显示 LLM 决策、参数变化、Guardrails 和审计入口；普通训练不渲染空白的调优专属区域。

## 8. 错误处理

1. 报告生成失败：保留训练成功状态，写入 `analysis_error`。
2. 历史持久化失败：返回明确的 `history_persistence_error`，不伪报完整收尾成功。
3. `results.csv` 缺失或无有效指标：分析失败或部分完成必须有明确原因，不补 0。
4. 重复回调或服务器重试：依靠稳定 `run_id` 保证幂等。
5. 旧历史损坏：忽略损坏的兼容来源并返回可诊断警告，不破坏新的实验历史。

## 9. 测试与验收

### 9.1 自动化测试

1. 普通训练成功后生成 Module B 报告、KPI 和统一历史。
2. 自动调优完成后写入同一实验历史。
3. 两类记录使用不同来源并在 UI 同表展示。
4. 训练成功但分析失败时状态语义正确。
5. 训练失败和取消时生成相应历史记录。
6. 缺失指标不补 0，真实零值保留。
7. 相同 `run_id` 重复收尾不产生重复历史。
8. 原子写入失败不破坏旧历史。
9. 旧调优历史兼容映射并去重。
10. SSE 完成事件携带统一结果结构。
11. UI 来源筛选、状态筛选和条件详情渲染正确。
12. 现有 A0 审计和完整测试无回归。

### 9.2 真实验证

1. 使用 1 epoch 完成一次普通训练，验证 KPI、报告、历史和 UI。
2. 使用自动调优 dry-run 验证历史结构；如需验证真实 after 指标，再执行一次 1 epoch 自动调优训练。
3. 对照 `results.csv` 最终行、Module B 报告、统一历史和界面显示，四处指标必须一致。

## 10. 完成标准

本批只有同时满足以下条件才可验收：

1. 普通训练与自动调优共用统一收尾服务。
2. 两类训练都进入统一实验历史。
3. 训练状态和分析状态不会相互覆盖。
4. UI 能自然区分来源并展示统一 KPI。
5. 重复收尾、分析失败和持久化失败均有测试。
6. 完整测试通过。
7. 真实短训练的 `results.csv`、报告、历史和 UI 指标一致。
8. 文档回写实际完成状态与测试证据。

本批验收完成后，再准备项目的第一次 GitHub 源码版本上传；上传范围不包含数据集、训练权重、训练产物、日志或密钥。
