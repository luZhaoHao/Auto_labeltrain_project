# Auto-Tune Studio — controlled Windows runtime dependencies (F1.2-D).
#
# Identical to docker/requirements-runtime.txt on purpose: one verified runtime,
# two deliveries. A package must never have two versions depending on how the
# product was installed, so the Windows lock is a copy of the accepted container
# lock and a test asserts the two files stay equal.
#
# Scope: only what the Studio needs at runtime.
#   * every package imported by production code under auto_tune/ (excluding
#     tests and scripts);
#   * the packages Ultralytics needs to run a training job;
#   * the packages the HPO module needs (Optuna and its declared backends);
#   * the ONNX export stack the F1.2-A channel uses.
#
# Provenance: pinned from the independently accepted F1.1 environment
# (environment.yml, Python 3.10), plus the five HPO pins recorded in
# auto_tune/requirements.txt. The root requirements.txt and the stale
# auto_tune/requirements.txt are deliberately NOT merged here: their loose
# bounds and unused entries (gradio, httpx) are not part of the verified
# runtime.
#
# Deliberately absent on Windows too:
#   * torch / torchvision — installed by windows/lib/AutoTuneDelivery.psm1 from
#     the pinned CUDA 12.1 PyTorch wheel index before this file. Adding them
#     here would let pip resolve a CPU wheel over the CUDA build.
#   * pytest, pluggy, iniconfig, exceptiongroup, tomli — test-only.
#   * pyreadline3 — a development-shell convenience, not a runtime import.
#   * onnxruntime-gpu — export is pinned to device=cpu (see
#     onnx_export_worker.EXPORT_DEVICE) and training runs on torch.
#   * onnxslim — Ultralytics requires it only for ``simplify=True``, and the
#     export arguments are frozen at simplify=False.
#   * httpx / gradio — the UI is FastAPI + Jinja2; these belong to the stale
#     root requirements list.
